# restore-worker

The native, privileged component that runs allowlisted PBS CLI commands on behalf of the Control Plane (manifest §3, §4.1, §15). Runs as a systemd service in the real appliance; packaged here (Milestone 0) as a plain Python library with tests, since systemd packaging is a Milestone 5 concern — **except** `resurgam-lab-agent` (see below), which has real `debian/` packaging today because it's a genuinely standalone, customer-installable daemon, not an in-process library called by `backend`.

## What's here

- `capability/` — detects whether this host can support file-restore: PBS client presence/version, `/dev/kvm`, `/dev/fuse`. Never raises for a missing capability; always returns a structured report (manifest §18.12).
- `pbs_client/file_restore.py` — safe, fully-typed wrappers around four `proxmox-file-restore` subcommands (`list`, `extract`, `status`, `stop`) for VM/qemu snapshots. Confirmed live (2026-09-15) against a real PVE 9.2 node, and again (2026-09-16) on a dedicated Debian 13 nested-KVM dev VM — a real Windows Server VM backup's disk archive, partitions, and NTFS directory tree all listed and downloaded correctly, standalone (no PVE API involved). **Requires `proxmox-backup-file-restore`, `proxmox-backup-restore-image`, and `pve-qemu-kvm` to all be installed from the same PVE apt repo release** (not mixed with the separate PBS-only repo) on a matching Debian release, and (finding of 2026-09-16, **superseded 2026-10-07**) was thought to require root: the `EACCES` came from `proxmox-file-restore`'s state/log directories, which the appliance now makes writable for the unprivileged `resurgam-worker` via tmpfiles.d (`appliance/release/host-setup.sh`), so the workers run without root and without capabilities — see [`../docs/adr/0011-file-restore-in-process-restore-worker.md`](../docs/adr/0011-file-restore-in-process-restore-worker.md) for the real debugging story (an `AF_VSOCK`/AppArmor bug, a zombie-reaping bug, the version-mismatch root cause, and this root-privilege finding) and [`../docs/milestone-1-pbs-pve-api-assumptions.md`](../docs/milestone-1-pbs-pve-api-assumptions.md) for the environment notes.
- `pbs_client/catalog.py` — wrappers around `proxmox-backup-client catalog dump`/`restore` for CT/host (pxar-based) snapshots. Built and confirmed live against a real PBS 4.2 instance (2026-09-14/15) — see [`../docs/adr/0011-file-restore-in-process-restore-worker.md`](../docs/adr/0011-file-restore-in-process-restore-worker.md) for the real, non-obvious tool behaviors (stderr vs stdout, `--pattern`, `--ignore-ownership`) that live testing caught and this wrapper works around.
- `pbs_client/map.py` — wrappers around `proxmox-backup-client map`/`unmap`/`snapshot files` (manifest §10.4/§12, previously listed below as a later-milestone item — now here). Confirmed live (2026-09-19) against a real PBS 4.2 instance: a real 130MB VM disk archive mapped as `/dev/loop0` with **zero copy** (a genuine readable MBR disk, `fdisk -l` confirmed a real partition table), and cleanly unmapped afterward (`losetup -a` confirmed empty). This is the real mechanism behind Recovery Lab (ADR 0019) — deliberately *not* `qmrestore --live-restore`, which was live-tested and found to silently ignore a caller-supplied network override during its own internal VM start.
- `pve_client/qm.py` — local (not PVE-API) wrappers around `qm create`/`start`/`stop`/`destroy` and `qemu-img create` (for a COW overlay atop a mapped device). `create_vm`/`start_vm`/`stop_vm`/`destroy_vm`/`create_cow_overlay` all confirmed live (2026-09-19) against a real PVE 9.2 node, in two configurations: a VM booted read-only directly off a `map.py`-produced block device (`ro=1`), and a VM booted off a writable qcow2 COW overlay attached as `scsi0` (`qm status` showed `running`; the overlay file's size grew, 196KiB → 388KiB, confirming writes land in the overlay and never touch the backing device). One real prerequisite this uncovered: `qm` accepts a bare `/dev/loopN` path for `scsi0` directly, but rejects a bare qcow2 *file* path outright ("unable to associate path ... to any storage") — the overlay must live under a PVE-registered "dir" storage (`pvesm add dir <id> --path <dir> --content images`) and be referenced as `<storage-id>:<vmid>/vm-<vmid>-disk-0.qcow2`, which is why `lab_agent.config.LabAgentConfig` has an `overlay_storage_id` field the operator must provision alongside `overlay_dir`.
- `lab_build/` — the probe appliance and share helper template builds (moved here from the backend, ADR 0027), run over SSH by the backend or locally by a paired agent through the same `Shell`/`BuildLog` protocols.
- `lab_agent/` — the actual `resurgam-lab-agent` daemon (ADR 0019): polls RESURGAM's backend (`GET /lab-agent/jobs`, a cluster-scoped bearer token, never a database connection) for Application Group members ready to test, and for each one runs `pbs_client.map` + `pve_client.qm` to map, overlay, attach, and boot it, then reports status back (`POST /lab-agent/jobs/{id}/status`). `config.py` reads its own local env-var config (required: `RESURGAM_BACKEND_URL`, `RESURGAM_LAB_AGENT_TOKEN`; optional since 0.2.6: `RESURGAM_LAB_AGENT_PBS_TOKEN` — without it the agent only runs template builds and appliance snippet jobs, while lab runs, ephemeral file indexing and disk mounts wait for it; `RESURGAM_LAB_AGENT_CA_FILE`, `RESURGAM_LAB_AGENT_NODE_NAME`, ... — all documented in `debian/resurgam-lab-agent.default`) — **the backend never sends PBS credentials over the wire**, only coordinates (host/port/datastore/namespace/snapshot); this agent authenticates to its own locally-configured PBS instance(s) itself, matching this package's existing local-config precedent rather than inventing per-job credential passing. Entrypoint: `resurgam-lab-agent` (`[project.scripts]`, `lab_agent.daemon:run_forever`).

Every subprocess call in every wrapper module uses an explicit argument list (`subprocess.run([...])`), never a shell string. `file_restore.py`'s CLI JSON output is parsed strictly into versioned Pydantic models — malformed or unexpected JSON raises a typed error rather than being passed through as a dict. `catalog.py`/`map.py`'s plain-text output is parsed with a documented, fixture-tested regex.

Called in-process from `backend/` (`resurgam_api/filerestore/browse.py`), via an editable path dependency — see ADR 0011. `lab_agent`, by contrast, is **never** called from `backend` in-process — it's a genuinely separate deployable, talking to `backend` only over its own HTTPS API.

## `resurgam-lab-agent` packaging

`debian/` in this directory builds a real `.deb` (dh-virtualenv-based — bundles this package's exact pinned deps into `/opt/venvs/resurgam-lab-agent` rather than depending on a given Debian release's own `python3-pydantic`/`python3-httpx` versions) with a systemd unit (`resurgam-lab-agent.service`, runs as root — required, same finding as `file_restore.py`'s own root requirement above) and an `/etc/default/resurgam-lab-agent` config template (a real dpkg conffile, survives upgrades).

**Built with every backend image** (2026-10-07): `backend/Dockerfile`'s `lab-packages` stage runs `dpkg-buildpackage -us -uc -b` here on `debian:trixie` (build-deps: `build-essential debhelper dh-virtualenv virtualenv dpkg-dev python3-dev python3-venv`; `virtualenv` must be installed explicitly with `--no-install-recommends`) and copies both `.deb`s plus a `manifest.json` (`appliance/release/lab_artifacts_manifest.py`: name, version, SHA-256, Debian release) to `/app/artifacts` in the image. The backend serves them for download; the agent is installed by pairing a node with a one-time code (ADR 0027) or over a one-time SSH session, and `resurgam-lab-prober` is baked into the probe appliance template from there — by the paired agent on its node or over SSH (build code: `lab_build/`; backend side: `backend/src/resurgam_api/lab_setup/`). Because dh-virtualenv links the build host's Python, the packages run on Debian 13 (PVE 9) only (ADR 0020).

### Versioning

The packages ship inside every image and update bundle, so they carry the release version: **`debian/changelog`'s upstream version must equal the repo-root `VERSION`**; only the Debian revision (`-N`) is free (bump it for a packaging-only fix within a release). When bumping `VERSION`, add a changelog entry first (`dch -v <VERSION>-1`, or edit `debian/changelog` by hand). Three places enforce it: the image build (`lab_artifacts_manifest.py` refuses a mismatch), `appliance/release/build-bundle.sh` (checks before building anything) and the backend test suite (`test_debian_changelog_upstream_version_matches_VERSION`). `pyproject.toml`'s own `version` is the Python distribution's and is not used for the packages.

An operator still needs the overlay `dir` storage (`pvesm add dir <overlay_storage_id> --path <overlay_dir> --content images`, or the Lab Compute wizard's auto-fix) before the agent's first job. The project's license is decided (AGPL-3.0-or-later, see the repo root's `LICENSE`) and `debian/copyright` reflects it.

## What's deliberately not here

- Any DB/queue access of its own. As of ADR 0013 (2026-09-16), file-restore listing/downloading is consumed from a Postgres-native job queue (ADR 0002) by a separate worker process — but that consumer lives in `backend/src/resurgam_api/worker/file_restore_worker.py`, not here, specifically so this package stays dependency-light rather than gaining SQLAlchemy/DB access or inverting the `backend → restore-worker` dependency edge. That worker process still calls this package's functions directly, in-process, unchanged. `lab_agent` follows the same discipline via a different mechanism (HTTPS instead of DB polling, ADR 0019), for the same underlying reason: it must run on infrastructure that never runs `backend` at all.
- systemd packaging for anything *other* than `resurgam-lab-agent` (Milestone 5 appliance-packaging concern for the rest of this project, unaffected by `lab_agent`'s packaging above).
- Sandboxing/allowlist enforcement at the OS level beyond running as root (Milestone 5).
