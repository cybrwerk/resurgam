# 0014 — Automated Restore Orchestration (EPIC 9): in-process execution, pull-triggered finalize, four-eyes approval

Status: Accepted (2026-09-17)

## Context

EPIC 8 (Guided VM/CT Restore, ADR 0012) produces a `RestorePlan` row: a reviewed, live-checked plan plus a generated `qmrestore`/`pct restore` **command as text** for a human to run by hand. Nothing executed — deliberately. `RestorePlan`'s own docstring reserved `executed_at`/`upid`/`ttl`/`cleanup_status` for "EPIC 9's own future migration."

Manifest §11.2 defines that epic: start the restore via the PVE API (not the CLI), store the UPID and track progress, leave the VM off by default, disconnect network cards by default (or place them in an isolated restore network), optionally enforce four-eyes sign-off, generate a complete audit event.

**This is the first RESURGAM feature that actually mutates a customer's live PVE infrastructure** — every prior feature was read-only or advisory. That materially raised the bar for this work: real confirmations, safe defaults, and PVE REST behavior verified live before being trusted, not assumed from the CLI's already-verified behavior.

## Decision

**Stays in-process, no new worker/queue.** The file-restore job queue (ADR 0013) was justified by root privilege (VM file-restore) and multi-minute blocking subprocess calls — neither applies here: starting a PVE restore is a single outbound `POST` returning near-instantly with a UPID; the restore itself runs on the PVE node, not on a RESURGAM request thread.

**The finalize step (network lockdown, optional start) is pull-triggered and idempotent**, not inline in `execute`. `execute` only fires the restore call and stores the UPID. `POST /restore-plans/{id}/execution/poll`, called by the frontend on a timer, fetches the live task status and — the first time it observes completion — performs the finalize call(s) in that same request before returning. This mirrors the existing `recheck` endpoint's shape (a POST doing live external I/O plus a DB write), not a new pattern. It also means a RESURGAM restart mid-restore is a non-event: all state lives in Postgres, the next poll just resumes against PVE's own UPID.

**No lease/heartbeat — but a TTL-based staleness check, evaluated inline on each poll, added after initial ship (and corrected once more the same day).** The first design left restore-execution with no automatic recovery at all if a PVE task genuinely hung: unlike the file-restore job queue (which has a background worker sweeping stale jobs on a timer), this feature has no worker process, so a stuck task would sit in `restore_running` forever between polls. The first fix checked staleness *before* even calling PVE — which was itself a bug, raised directly by the user: a restore of a large disk can legitimately run for hours, and force-failing it purely because our own clock says "too long" while PVE is still honestly reporting `running` corrupts the record for something that may well still succeed. Corrected design: `poll` always asks PVE first; a **reachable** answer is authoritative regardless of elapsed time (never overridden by the staleness clock); staleness (`is_execution_stale`, anchored on the new `execution_last_confirmed_at` column — the last time PVE was successfully reached, not `executed_at`) only fires when PVE itself has been **unreachable** for longer than `settings.restore_execution_stale_after_seconds` (default 4 hours), and the resulting error message says so explicitly ("could not reach PVE... the restore may have completed independently — check PVE directly") rather than implying the restore itself failed. Still fundamentally pull-driven, not a real sweep — a plan nobody ever polls again still won't self-heal — an accepted limitation of not building a worker process for this feature, not a full replacement for ADR 0013's pattern.

**Four-eyes approval**: a per-cluster opt-in toggle (`PveCluster.require_restore_approval`, default off). `RestorePlan.approval_status` is set to `pending` at creation time if required, but enforcement happens at the `execute` gate regardless of when it was set — decoupling "visible in the list view" from "safe to execute." The plan's own creator can never approve or reject it (`403 self_approval_forbidden`, deliberately not the codebase's usual 404-for-denial — the creator already knows their own plan exists, so 404 would misrepresent the reason for denial). `platform_admin` is not exempt from this check. Any `restore_operator` scoped to the plan's customer may approve a colleague's plan — no new role was invented.

**One execution attempt per plan.** A failed execution leaves the plan terminal; retrying means creating a new plan, which re-validates live PVE state (worth doing again after a failure) rather than modeling attempt/retry history.

**The existing-VMID overwrite case gets a stronger confirmation than EPIC 8's checkbox pattern**: the operator must type the exact target VMID before `Execute` enables, since this case is genuinely destructive (`--force`, overwrites the existing guest's disk) in a way network-mode risk isn't.

## Real findings from live verification (2026-09-17, real PVE 9.2 cluster, disposable VMIDs, VM 116/tenant-a's real backup)

Two real, previously-unpredicted PVE privilege gaps, found only by actually running a restore (matching ADR 0011's own discipline of granting exactly what a live `403` reveals is missing, not a broad role upfront):
- `SDN.Use` on the VM's referenced SDN zone — checked by PVE *during the restore itself* (before any of RESURGAM's own network-finalize logic runs), for any backup whose archived network config references an SDN-managed zone.
- `VM.Config.Options` — required to apply `name` (see below), separate from `VM.Allocate`/`VM.Config.Disk`/`VM.Config.Network`/`VM.PowerMgmt`.

Two real product bugs found and fixed mid-build, both only discoverable by actually running a restore rather than reading CLI docs:
- **The restored guest kept its original archived name, not RESURGAM's `temp_name`.** True of EPIC 8's CLI-text generation too, just never provable until EPIC 9 actually ran a restore — `check_name_conflict` was checking a name that was never applied to anything. Fixed by adding `name` (VM, confirmed live) / `hostname` (CT, **not yet verified live** — only a VM restore was exercised this pass) to the restore call, in both the real execution path and the EPIC 8 CLI-text generator. The auto-generated default `temp_name` now also prefers the backup group's real `resolved_name` (PBS's own reported guest name) over the bare backup id, when known.
- **"None" network mode deleted the NIC outright (`qm set --delete net0`) instead of disconnecting it.** Raised directly by the user: a deleted NIC is less reversible and can surprise a guest OS that expects the device to still be present, just unplugged — CT's own restore command already disconnected (`link_down=1`) rather than deleted, but with a hardcoded `vmbr0` fallback bridge that may not even exist on a given cluster. Fixed for VM by reading the restored guest's actual config back (`GET /nodes/{node}/qemu/{vmid}/config`, new `pve_api.get_vm_config`) and re-`PUT`ting the same `net0` value with `link_down=1` appended (`restore/execution.py`'s new `with_link_down`) — confirmed live: the real MAC, model, and SDN-managed bridge (`vlan005`) were all preserved exactly, only `link_down=1` added. EPIC 8's CLI-text generator gained the equivalent real, runnable one-liner (`qm set {vmid} --net0 "$(qm config {vmid} | awk -F': ' '/^net0/{print $2}'),link_down=1"`) so the manual-restore path stays honest too.

## Consequences

- `restore/execution.py` stays fully unit-testable (no PVE I/O) even with the `current_net0`-aware finalize logic — the API layer (`api/v1/restore_execution.py`) does the one extra `get_vm_config` read and passes the result in, keeping the pure-function boundary intact.
- CT restore-execution (the `hostname`/inline-`net0` params, `CT_RESTORE_SUPPORTS_INLINE_NET0`) remains documented-but-unverified — flagged explicitly in `docs/milestone-1-pbs-pve-api-assumptions.md` as a follow-up live-verification item, not assumed safe by extension from the VM path.
- The `SDN.Use`/`VM.Config.Options` grants are specific to this test cluster's actual network topology (SDN zones) and guest configs; a different cluster's backups may reveal other privilege requirements the same way — expected, not a design flaw, given the "grant what a live error reveals" discipline this project has used consistently since ADR 0011.
