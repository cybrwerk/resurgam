# 0016 — Persistent File Indexing

Status: Accepted (2026-09-17)

## Context

Manifest §13 originally deferred "persistent File Indexing" out of MVP scope: the MVP browses a snapshot's files on demand only (`proxmox-file-restore list`/`catalog dump`, ADR 0011/0013). While discussing better progress UX for that on-demand browsing flow, the user explicitly reopened this deferred scope: a later, optional-per-customer global search over backup contents, storing only metadata — snapshot, backup group, archive/disk, path/filename, type, size, timestamp — never file contents. Index jobs need I/O limits, time windows, cancellation, progress, and customer-specific retention (manifest's own wording).

Confirmed with the user before design: v1 indexes both CT/host and VM disks (not CT/host-only); triggers are manual per-snapshot, manual bulk per-group, and recurring/scheduled; scheduling is poll-based and scoped only to this feature (no general-purpose scheduler — none exists anywhere yet, ADR 0006); a configured time window blocks starting a job and auto-pauses a running one, uniformly across every trigger type; filename search supports substring matches (`pg_trgm`), not just prefix; config (opt-in/retention/schedule/window) is separate from the search UI; deleting a customer's settings cascades a purge of their indexed entries.

## Decision

**A second, separate privileged worker process** (`worker/file_index_worker.py`, `resurgam-file-index-worker` entrypoint), not a third job type folded into `file_restore_worker.py`. Read directly: that worker's `run_forever()` is fully sequential (claims one job, runs it to completion, only then loops back) — sharing it would block every interactive list/download request for the duration of a multi-hour index job. Both workers need root for the same reason (VM file-restore beyond top-level listing, ADR 0011/0013).

**Three new tables** (migrations 0019–0021):
- `file_index_jobs` — one row per (group, snapshot) index attempt; a bulk "index all" trigger creates N rows, not one iterating row, so it reuses the same claim/progress/pause/cancel machinery as a manual trigger. No `expires_at`/TTL (unlike `FileRestoreJob`) — a job can be legitimately `paused` for hours (its window closed), which a single deadline can't distinguish from a crashed worker; staleness is instead a `last_heartbeat_at` timeout, updated at every checkpoint including "just paused."
- `file_index_entries` — the manifest's named fields exactly, CASCADE FKs (pure derived data), a functional GIN trigram index on `filename` for substring search (`pg_trgm`, this codebase's first use of a Postgres extension beyond the base image), and a unique `(file_index_job_id, path)` constraint enabling `ON CONFLICT DO NOTHING` upserts.
- `customer_file_index_settings` — one row per customer (`customer_id` UNIQUE NOT NULL, unlike `PricingPlan`'s nullable-customer-id sparse-default pattern — there's no meaningful global default here): `enabled`, `retention_days`, `schedule_enabled`/`schedule_interval_hours` (interval-since-last-run, not cron), `window_start_time`/`window_end_time` (UTC time-of-day), `next_scheduled_run_at`.

**Worker loop**: claims `pending`/`paused` jobs (`FOR UPDATE SKIP LOCKED`); a coarser-cadence scheduled-enqueue pass inserts one `pending` job per (customer, snapshot) that's both due and not already indexed/in-flight; an even coarser retention sweep purges entries past each customer's `retention_days`. Per-job checkpointing (after each insert batch for CT/host, after each directory for VM) checks, in order: the time window (persist cursor, `paused`), cancellation (`cancel_requested`, keep partial entries, `cancelled`), and — VM only — a self-imposed per-run directory-visit budget (persist cursor, back to `pending`, immediately re-claimable). CT/host does one `dump_catalog()` call (confirmed live elsewhere: ~63k entries, 0.55s) and batches the insert; VM does a BFS over directories via `list_path()`, one subprocess call each, throttled by a configurable inter-call delay — the concrete "I/O limit" the manifest asks for on the expensive path.

**Prune-detection scoped narrowly to this feature.** `collector/sync.py`'s `sync_datastore_inventory` deliberately never deletes `backup_snapshots` rows for snapshots PBS no longer reports (ADR 0006, unchanged by this work) — but a `file_index_entries` row pointing at data PBS has already pruned is a sharper problem than an ordinary stale inventory row: it actively invites a restore attempt against data that no longer exists. A new `_purge_orphaned_file_index_entries`, using the snapshot list that sync already fetches, purges index entries (not `backup_snapshots` rows) for any snapshot missing from that live list — including every entry of a backup group PBS no longer reports at all.

**No differential/incremental indexing across snapshots.** Confirmed via the wrapped tools' own behavior: `dump_catalog()` always returns the entire catalog, `list_path()` always returns a full directory listing — neither exposes a "since" or diff mode, so a new snapshot is always walked in full. What the design gives for free instead: since PBS snapshots are immutable, `_snapshot_has_live_index` means a given snapshot is walked at most once, ever — a scheduled run only pays the cost of genuinely new snapshots.

**API** (`api/v1/file_index.py`): job creation (manual per-snapshot, bulk per-group), get/list/cancel, `GET /file-index/search` (customer-scoped, `has_more`-based pagination rather than `COUNT(*)` over a potentially huge table), and full settings CRUD including `DELETE`, which purges the customer's `file_index_entries` in the same transaction rather than leaving orphaned index data with no config left to explain its retention.

**Frontend**: a new `/recovery/file-index` page (search + per-group job monitor with cancel), trigger buttons on the existing `FileRecoveryPage` gated on the customer's settings showing `enabled: true`, and a new "File Index" section in `CustomersPage`'s existing per-customer detail modal (own query, own independent mutations, mirroring how the billing section already works there).

## Live verification (2026-09-17)

Run against real Sample Customer AG data (`pbs1.example.internal`), from a fresh install on the Debian 13 dev VM (native `apt` PostgreSQL 17, not the project's usual docker-compose image) — the full migration history (0001-0021) applied cleanly from empty, and a real `sync_datastore_inventory` pulled 136 real backup groups / 1367 real snapshots.

- **CT/host** (`ct/100`, namespace `tenant-a`): fully indexed end to end — 63,389 real entries (directories, files, symlinks), correct sizes/mtimes, in ~27s.
- **VM** (`vm/116`, namespace `tenant-a`, a real Windows Server disk): BFS walk confirmed against real content (`Program Files`, `Boot/BCD`, etc.), correct per-entry archive attribution (`drive-sata0.img.fidx`); the directory-budget checkpoint correctly stopped after exactly the configured count, persisted its cursor, and a second call resumed from it with entries accumulating (137 → 373), not resetting.
- **Time window**: a job created with a currently-closed window went straight to `paused` with zero PBS calls, confirming the window blocks *starting* a job uniformly, not just running ones.
- **Cancellation**: the real `resurgam-file-index-worker` process claimed a job, started running it against real PBS, and a `cancel_requested` flag flipped from a *separate* database connection while it was mid-run was correctly observed at the next checkpoint — `cancelled`, with the entries indexed before the flag flip kept (373 → 378, not discarded).
- **Substring search**: `EXPLAIN` on a real `ILIKE '%grub%'` query against the 63k-row CT index confirmed Postgres's planner actually chooses `ix_file_index_entries_filename_trgm` (Bitmap Index Scan), not a sequential scan — 35ms/6ms for two real substring queries.

**A real, pre-existing bug was found and fixed along the way**, not part of this feature's own new code but exposed by it: `filerestore/browse.py`'s `snapshot_identifier()` formatted `snapshot.snapshot_time.strftime('%Y-%m-%dT%H:%M:%SZ')` without first normalizing to UTC. `collector.sync` stores this column UTC-normalized, but Postgres converts a `timestamptz` column to the *session's* timezone on read — the project's own docker-compose Postgres image defaults to UTC (masking the bug in every previous live-verification pass this session), but a freshly `apt`-installed PostgreSQL on the dev VM inherited the host's local timezone (CEST, UTC+2), so a real snapshot stored as `...T00:00:04Z` came back as `...T02:00:04+02:00` — correctly representing the same instant, but naively re-labeled with a literal `Z` it produced a snapshot identifier two hours off the real one, which PBS correctly rejected as "does not exist". Fixed with an explicit `.astimezone(timezone.utc)` before formatting; a regression test (`test_filerestore_browse.py`) pins the exact scenario. This affects every caller of `snapshot_identifier` (the on-demand file-restore/browsing path too), not just File Indexing — a real, previously-undetected bug this feature's live verification against a differently-configured Postgres instance happened to surface.

## Consequences

- Two privileged daemons must now run in dev (`sudo uv run resurgam-file-restore-worker` and `sudo uv run resurgam-file-index-worker`, both from `backend/`) — more operational surface than one, accepted deliberately over building cooperative multitasking into the shipped file-restore worker.
- `pg_trgm` is genuinely new infrastructure in this codebase — the migration enables it with `CREATE EXTENSION IF NOT EXISTS`, confirmed to apply cleanly against the dev database.
- `filerestore/browse.py`'s `_repository_and_token`/`_snapshot_identifier`/`_CT_HOST_ARCHIVE_NAME` were renamed to public (`repository_and_token`/`snapshot_identifier`/`CT_HOST_ARCHIVE_NAME`) so the new `filerestore/index_entries.py` module can reuse them without duplicating PBS repository-string/token-retrieval logic — a pure rename, no behavior change, covered by the existing file-restore test suite passing unchanged.
- The VM path's real subprocess-volume cost (one `proxmox-file-restore list` call per directory) is bounded by a configurable inter-call delay and a per-run directory budget. Confirmed live: the restore-VM session is indeed reused across calls within one walk (only the first call pays a cold-boot cost; the 15-directory budget test above completed in well under 10s total, consistent with warm, not per-call cold-booted, listing) — the earlier concern about the VM path being dominated by repeated multi-second cold boots did not materialize in this real (if not exhaustively deep) walk.
- Substring filename search depends on the new trigram index; a customer/group-scoped query still benefits from the composite `(customer_id, backup_group_id)` btree alongside it for the common filtered case.

## Addendum (2026-11-12): beta run on the appliance

A first full run on the real appliance (the test appliance, release 0.2.8) against a real PBS found three things, all fixed:

- **The schedule queued a snapshot's whole history.** The scheduled-enqueue pass queued one job for *every* not-yet-indexed snapshot of a group. The "only genuinely new snapshots" reasoning above holds once a group is caught up, but on first opt-in every existing snapshot counts as new: a VM with 395 snapshots would have queued 395 jobs of up to hours each. A scheduled run now queues **only the group's newest snapshot**, if it isn't indexed, in flight or already completed (a completed job that stored nothing — e.g. everything excluded — counts as done, so it isn't re-queued every run; a failed one is retried). Older snapshots remain indexable on demand (manual / bulk).
- **Kernel headers and modules dominated Linux VM indexing.** On a 100 GB Ubuntu VM, 188k of 251k entries (75%) were `/usr/src/linux-*` and `/lib/modules` — one copy per installed kernel. Both are now in the default exclude list; migration 0066 adds them to every group still on the unmodified previous default (operator-edited lists are left alone).
- **The inter-call delay was most of the runtime.** 0.2 s per directory × 34k directories ≈ 1 h 55 min of the job's 2 h 51 min; a listing itself took ~0.1 s. Default lowered to 0.05 s (still configurable, `FILE_INDEX_WORKER_VM_CALL_DELAY_SECONDS`).

Also: the native file-index and file-restore workers could start before the Dockerised Postgres at boot and crashed once each (systemd restarted them). Both now wait for the database (`db.wait_for_database`), and the file-index loop retries on a lost connection instead of exiting.

Measured on the same run: a CT backup (Alpine, 242 MB) indexed in 0.8 s; the restore helper VM shut itself down ~11 minutes after the job finished.

A second run (0.2.9, 2026-11-13, a German Windows 11 VM and a Linux Mint VM) found more; both jobs were cancelled and re-run on the fixed release:

- **Transient errors were treated as "not mountable".** `proxmox-file-restore list` once answered an ordinary Windows directory with `Unable to acquire lock ".../tasks/.active.lock" - Interrupted system call (os error 4)`, in the same `{"code", "message"}` shape as a genuinely unmountable partition, so the directory was skipped and silently missing from the index. `list_path` now retries such lock/EINTR answers (0.5 s, 2 s, 5 s) before falling back to the skip.
- **NTFS compatibility junctions are listed as plain directories.** `Dokumente und Einstellungen`, `Programme`, `Users/<user>/Anwendungsdaten`, `Startmenü/Programme` etc. are reparse points, but `list` reports them as type `d` with no distinguishing metadata, so the walk followed them and indexed `Users` and `Program Files` a second time (174k duplicate entries under `Dokumente und Einstellungen` alone). There is no reliable way to detect a junction from the listing, so the known English and German junction names are default excludes, anchored to where Windows creates them (a user's own `Documents/Vorlagen` is still indexed). Other Windows languages have their own junction names; operators add them per group.
- **OS payload that isn't user data:** `Windows/servicing/LCU` (the unpacked cumulative update, >136k entries, ~35% of the Windows index), Timeshift's own system snapshots (2.96M of 4.99M entries on the Mint VM) and `usr/share/icons` (1.73M). All three are default excludes.

Migration 0067 adds all of these to groups still on the unmodified default list.

The first scheduled run of the three-day test (0.2.10, 2026-11-14) found one more:

- **The newest snapshot can be short-lived.** For a VM and a CT backed up every two hours, the 05:00 run indexed the 03:00 snapshot; PBS prune removed it before noon and the index went with it (correctly, see `_purge_orphaned_file_index_entries`). For such groups the schedule now indexes **the newest snapshot of the last finished day**: PBS prune keeps the newest snapshot of each day (`strftime_local("%Y/%m/%d")` in `pbs-datastore/src/prune.rs`), so this is the one `keep-daily` keeps. PBS counts days in its own local time, so the Collector now stores each PBS server's timezone (`GET /nodes/localhost/time`, readable by any token; `pbs_instances.server_timezone`, migration 0069). A group counts as "several backups per day" when at least 2 of its last 7 days hold more than one snapshot, so one extra manual backup doesn't change a nightly group, which still indexes its newest snapshot. Only snapshots the newest Collector pass still saw are candidates (RESURGAM keeps rows of pruned snapshots, ADR 0006). Trade-offs: the index of such a group is up to a day behind its newest backup; and a prune policy without `keep-daily` (e.g. `keep-last` only) keeps no snapshot for long, which no choice can fix.
