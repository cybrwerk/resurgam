# 0012 — Guided restore is a persisted, traceable plan; PVE connectivity gains live-probing

Status: Accepted (2026-09-16)

## Context

The user asked to work toward manifest EPIC 10 ("Scheduled Recovery Verification Lab" / RESURGAM Recovery Lab). Investigation showed EPIC 10 depends on EPIC 8 (Guided VM/CT Restore) and EPIC 9 (Automated Restore Orchestration), neither of which existed yet, and EPIC 10 itself needs a scheduler (deferred, ADR 0006), SDN network isolation, and a whole separate `resurgam-lab-agent` component. Building a real Recovery Lab now would mean building on a foundation that isn't there. EPIC 8 (§11.1 "MVP: geführter Restore") is the real, buildable foundation: a wizard that picks a snapshot and a restore target, runs live checks against the target PVE cluster, and generates a reviewed `qmrestore`/`pct restore` command — explicitly **not** auto-executed (§11.1: "Im MVP wird der Restore nicht automatisch gestartet"; automated execution is EPIC 9, a separate later epic).

PVE connectivity before this slice was exactly one function (`probe_pve`, a version check) — no node, storage, or VMID listing existed anywhere in the codebase, confirmed by exhaustive search. This is greenfield backend work.

## Decision

**PVE connectivity gains a shared `_get_data` helper and four live-probe functions**, mirroring `connectivity/pbs_api.py`'s established pattern rather than inventing a second one: `list_nodes`, `list_storages(node)`, `list_guests`, `check_vmid_free`/`next_free_vmid`. All four were live-verified against a real PVE 9.2 cluster (the same `Sample PVE` instance already configured in this environment) before being trusted, via direct `curl` calls using the cluster's own already-stored API token, then re-verified through the actual Python functions once written:

- `GET /storage` (cluster-wide config) and `GET /nodes/{node}/storage` (per-node live status) are genuinely different endpoints with disjoint field sets — a `type: "pbs"` storage's `server`/`datastore`/`namespace` fields only appear on the former, `avail`/`used`/`total` only on the latter. `list_storages` merges both by `storage` id.
- A PBS-backed PVE storage is scoped to exactly **one PBS namespace**, not a whole datastore — confirmed live (the real `pbs-main` storage carried `namespace: "tenant-a"`). This directly informed `check_pbs_storage_visibility`'s namespace-matching logic, and was confirmed correct end-to-end in the live wizard walkthrough below.
- `GET /cluster/nextid?vmid=N` returns HTTP 400 with `{"errors": {"vmid": "VM <n> already exists"}}` for a taken VMID — a real, expected outcome (`free=False`), not a connectivity error, so `check_vmid_free` distinguishes it explicitly rather than surfacing it as one.
- A real bug was caught during this same live cross-check: an NFS storage's own generic `server` config field was initially leaking into `RemoteStorage.pbs_server` (which should only ever be populated for `type: "pbs"` entries) — fixed and covered by a regression test using the real `ISO-NTL` storage's shape as the fixture.
- `GET /cluster/resources?type=vm` is cluster-wide, not per-node, since VMID uniqueness is cluster-wide in PVE (matches ADR 0009's caution about not assuming per-instance uniqueness).

**`RestorePlan` is a real, persisted, auditable row** (`models/restore.py`, migration `0014`), not a stateless computed response — the manifest calls the wizard's output a "nachvollziehbarer Restore-Plan" (traceable plan), and this project's own precedent (`AuditEvent`, `ProtectionPolicy`) treats anything meant to be reviewed or cross-referenced later as a real record. Deliberately excluded: `executed_at`, `upid`, `ttl`, `cleanup_status` — those belong to EPIC 9's own future migration once automated orchestration actually exists; adding them now as unused columns would misrepresent what this feature does. `POST /restore-plans` rejects with 502 and persists nothing if the target PVE cluster is unreachable — a plan whose checks couldn't actually run isn't a traceable plan.

**`PveCluster.restore_network_rules`'s JSONB shape is defined here for the first time** (previously an unused, opaque field): `{"production_bridges": [...], "safe_bridges": [...], "default_bridge": "..."}`. An unconfigured cluster (`null`) never looks safe by default — same discipline as `evaluate_protection_status`: no policy means `UNKNOWN`, not a pass.

**Checks and command generation are pure functions** (`restore/checks.py`, `restore/command.py`), taking already-fetched connectivity data and never touching the network themselves — fully unit-testable without mocking httpx. `qmrestore` does not accept an inline network override (unlike `pct restore`, which does), so a VM restore needing anything other than the snapshot's own network config gets a follow-up `qm set` line — standard, well-documented Proxmox VE CLI behavior; **not** re-verified against this specific node's man pages this session (SSH access used for the earlier ADR 0011 work was not available in this session), flagged as a residual, accepted gap the same way ADR 0011 flagged its own open items.

**RBAC**: the four new live-probe endpoints (`GET /pve-clusters/{id}/nodes|guests|vmid-check`, `GET /pve-clusters/{id}/nodes/{node}/storages`) are `platform_admin`-only, matching every existing `pve_clusters.py` route today — no new RBAC pattern introduced (confirmed with the user rather than assumed; a coarser "any `restore_operator`" option was considered and rejected for this slice). `POST /restore-plans` itself reuses `filerestore.py`'s exact scoped-access check (`platform_admin` or `restore_operator` scoped to the snapshot's effective customer, 404 not 403 out of scope) — extracted into `auth/scope.py`'s `require_restore_access` since it now has two call sites, replacing the module-local copy `filerestore.py` had.

**Frontend**: a new `Wizard` shell component (`components/Wizard.tsx`) — genuinely new to this codebase, no prior step-sequencing pattern existed — plain props-driven navigation, no state-machine library, kept restore-agnostic since EPIC 10's own Recovery Lab UI (manifest §26.7, the same section this wizard's 5-step shape comes from) will likely want the same shell later. A new `SnapshotPicker` component extracts the customer→group→snapshot cascading-Combobox pattern on its fourth use (previously copy-pasted three times across `FileRecoveryPage`, `ProtectedWorkloadsPage`, `DatastoresPage`) — those three existing, already-shipped pages were deliberately left on their own inline copies rather than migrated in this same slice, to avoid touching three tested pages for this feature; a follow-up could consolidate them.

The wizard's "Restore options" step **omits TTL/automatic-cleanup controls entirely** rather than showing a toggle that enforces nothing — replaced with a static note that those apply once automated orchestration (EPIC 9) exists. A fake-but-inert toggle would contradict this project's standing discipline against representing unbuilt functionality as working (see `navTree.ts`'s own comment about `IMPLEMENTED_PATHS`).

## Live verification

The full 5-step wizard was walked end-to-end (temporary Playwright install, directly-minted session token, cleaned up after) against real data: `Sample Customer AG`'s real VM 116 snapshot, the real `Sample PVE` cluster (already linked to `Sample PBS` in this dev environment), a genuinely taken VMID (100 — correctly flagged "Bereits belegt"/Already in use) and a genuinely free one (999999 — correctly flagged "Frei"/Free), storage selection correctly excluding the `pbs-main` PBS-type storage from the target-storage list, and a final created plan whose every check passed against live PVE state, including the namespace cross-check (`Storage 'pbs-main' backs datastore 'backup-store' (namespace 'tenant-a') on this node`) and the exact generated command:

```
qmrestore pbs-main:backup/vm/116/2026-06-28T00:45:09Z 999999 --storage local-lvm --unique 1
qm set 999999 --delete net0
# VM 999999 is left powered off.
```

Zero console errors throughout. The resulting `RestorePlan` rows were left in the dev database rather than deleted — there is deliberately no delete endpoint for this audit-style record, matching the "traceable plan" intent.

A follow-up live pass (2026-09-16) covered the two paths the first pass hadn't exercised: a **CT** restore (not just VM) using a real running container (CT 101, namespace `tenant-a`) with the **existing-VMID** intent (not just "new"), correctly producing `pct restore 101 pbs-main:backup/ct/101/... --storage local-lvm --force 1 --net0 name=eth0,bridge=vmbr0,link_down=1` with the check text "VMID 101 exists and will be overwritten by this restore." — confirming both the `--force`-vs-`--unique` branch and the CT command shape against real data for the first time. The same pass deliberately triggered the PBS-storage-not-configured failure path live, using a real CT snapshot (CT 1121) in a namespace (`site-b/tenant-b`) with no matching PVE storage entry, and caught a real bug: the resulting long, sentence-length check message overflowed its panel instead of wrapping. Root cause: `StatusBadge`'s own `.badge` class is itself CSS-Modules-scoped (hashed at build time), so a `:global(.badge)` override written from the page's own stylesheet silently targeted a class that doesn't exist in the rendered DOM at all — no error, just no effect. Fixed with a `className` passthrough prop on `StatusBadge` (additive; every other short-label usage of the component elsewhere in the app is unaffected) rather than reaching into another component's scoped styles from outside.

## Consequences

- EPIC 9 (actual automated execution via the PVE API) has a real, tested foundation to build on: the connectivity layer, the checks, and the persisted plan model all already exist and only need an execution step added, not redesigned.
- Recovery Lab (EPIC 10) still requires a scheduler, SDN isolation, and a `resurgam-lab-agent` component before it can be real — none of that changed here, and `/recovery/recovery-lab` correctly remains a nav placeholder.
- The `qmrestore` network-override behavior and both commands' exact flag semantics should be re-verified against a real node's man pages (or, better, an actual test restore) before this is relied on beyond a reviewed-by-a-human starting point — the MVP's own design (a human reviews and runs the command) is exactly what makes this an acceptable residual gap rather than a blocking one.
- Provisioning the missing PVE-side storage.cfg entry automatically ("connect this PVE cluster to a PBS tenant") was considered and explicitly deferred, not built: it's a *write* to shared PVE infrastructure, a different risk class than everything else in this slice, which only reads PVE state. `check_pbs_storage_visibility`'s failure messages were sharpened instead — a direct, actionable "PBS store not configured on this PVE node — please configure it in PVE" rather than a passive description — so a human can fix it, matching this slice's own philosophy of a human-reviewed step at the point of risk.
