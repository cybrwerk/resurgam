# PBS/PVE REST API assumptions to validate against real instances

Same spirit as [`milestone-0-assumptions.md`](./milestone-0-assumptions.md): the outbound HTTP client code in `backend/src/resurgam_api/connectivity/` (`pbs_api.py`, `pve_api.py`) was originally written from best-effort recollection of public documentation, not verified against a real server. **Both PBS and PVE are now verified** against real instances (2026-09-13/14, both read-only tokens, no writes performed) — see below for what's still open on each.

## PBS — verified 2026-09-13 against a real PBS 4.2 instance

- **Version endpoint** (`GET /api2/json/version`): confirmed. Reachable with just the API token (no separate auth step), returns `{"data": {"release": "<string>", "repoid": "<string>", "version": "<string>"}}` exactly as assumed.
- **Auth header** (`Authorization: PBSAPIToken=<tokenid>:<secret>`): confirmed — the full colon-joined `user@realm!tokenname:secret` string works exactly as RESURGAM already asked operators to provide it.
- **TLS**: confirmed HTTPS-only on the configured port; the tested instance used a real (Let's Encrypt) certificate, so plain `tls_trust_mode: "ca"` worked without needing fingerprint pinning — the fingerprint path itself remains separately tested against a locally-generated self-signed cert (`test_tls_pinning.py`).
- **Datastore listing** (`GET /api2/json/config/datastore`): confirmed shape `{"data": [{"name", "path", ...}], "digest": "..."}` — `path` is the right field name. **Correction**: `comment` is *omitted* entirely when unset, not sent as `null` — `entry.get("comment")` already handles this correctly since it defaults to `None` either way, so no code change was needed here, just confirmation.
- **Task listing** (`GET /api2/json/nodes/localhost/tasks`): the `node` field is confirmed always `"localhost"`. **Two real bugs found and fixed**: (1) the actual field names are `worker_type` and `worker_id`, not `type` and `id` as originally assumed — the old code did `entry["type"]`, which would `KeyError` on every real call, meaning `/pbs-instances/{id}/sync` and `/tasks` were completely non-functional against any real PBS before this fix. (2) PBS reports a *different* `worker_type` for a manually-triggered run versus its scheduled-job counterpart (`"prune"` vs `"prunejob"`, `"verify"` vs `"verificationjob"`, presumed `"sync"` vs `"syncjob"` and `"backup"` vs `"backupjob"` by the same pattern, though only backup/prune/prunejob/verificationjob/garbage_collection were actually observed) — `collector/sync.py`'s `_TASK_TYPE_MAP` now maps both variants to the same `TaskType`. Also confirmed: `status` is the literal string `"OK"` (uppercase) on success. **New finding, not previously assumed at all**: this endpoint defaults to returning only the 50 most recent tasks; a `limit` query parameter raises that (tested up to 500 returning exactly 500 of a larger total) — `list_tasks` now passes `limit=2000` by default. A single instance with more than 2000 tasks since the last sync will still miss the oldest ones beyond that; documented as a stated simplification in `pbs_api.py`, not fixed with full pagination in this pass. **Also confirmed as correct, not a bug**: PBS's task history includes non-backup system tasks (`aptupdate`, `logrotate`, ...) with `worker_type`s outside RESURGAM's five backup-lifecycle types — these correctly fall into `TaskType.UNKNOWN`, which is the intended behavior, not a gap to close.
- **Snapshot listing** (`GET /api2/json/admin/datastore/{store}/snapshots`): the tested instance's *root* namespace genuinely holds zero live snapshots, but its real backups turned out to live entirely under non-root namespaces (`tenant-a`: 30 groups, `site-b/tenant-b`: 75, `site-b/Firestorm`: 30 — 135 groups, 1317 snapshots total) — invisible to RESURGAM until this was actually investigated (2026-09-14), because **this endpoint is scoped to exactly one namespace per call and does not recurse** (`?ns=<name>`, defaulting to root when omitted; a `max-depth` parameter was tried and rejected outright, `400 schema does not allow additional properties`). `list_snapshots()` now calls `list_namespaces()` first and queries every namespace explicitly, aggregating the results — falling back to root-only if namespace listing itself is unreachable (e.g. an older PBS without namespace support). **Correction to the original assumption**: a namespaced query's response entries do **not** carry their own `backup-namespace` field back — the original code read `entry.get("backup-namespace", "")`, which would have silently mislabeled every non-root snapshot as root even if the namespace-scoping bug were fixed differently; each snapshot's namespace is now attributed from the query that returned it. Per-snapshot field shape now confirmed against 1317 real entries: `backup-type`, `backup-id`, `backup-time`, `verification: {state}`, `size` all match the original assumption exactly. **New fields observed**: each snapshot also carries its own `comment` (distinct from the per-*group* notes below), a `files: [{filename, crypt-mode, size}, ...]` array, and `protected`. **`comment` is now parsed and stored** (2026-09-20, corrected after a direct report that a customer's real workload names — visible in the PBS web UI — weren't showing up in RESURGAM despite the per-group notes fix below): confirmed live against a real customer's data that this per-*snapshot* field, not the per-*group* "notes" field, is where a PVE vzdump job's `{{guestname}}` notes-template result actually lands — 136/136 real groups had a non-empty snapshot comment vs. 0/136 with non-empty group notes. `sync_datastore_inventory` now treats the latest snapshot's `comment` as `resolved_name`'s primary source, ahead of group-notes. `files`/`protected` remain unparsed — out of scope, note for later if useful. **`owner` is now parsed and stored** (2026-09-14, requested directly): `RemoteSnapshot.owner`, taken from whichever snapshot the Collector synced most recently into `BackupGroup.owner`, confirmed live against real data — 135/135 groups on the dev PBS synced with a real owner value (e.g. `ntl@pbs`, `tenant-a@pbs`). Surfaced read-only next to the manual customer picker in the Datastores tree, purely informational — no auto-assignment logic reads it, per the same tenant-isolation caution as ADR 0009's rejected cross-instance VM identity idea.
- **Namespace listing** (`GET /api2/json/admin/datastore/{store}/namespace`): confirmed shape `{"data": [{"ns": "<path>"}, ...]}`, with the root namespace as `{"ns": ""}`. New endpoint (`list_namespaces()`), added specifically to fix the snapshot-listing gap above.
- **Group notes / "Comment"** (`GET /api2/json/admin/datastore/{store}/group-notes?backup-type=...&backup-id=...`): confirmed to exist and return `{"data": "<text>"}`, with an empty string (not `null`, not a 404) for a group with no note set — now confirmed for **both** root and a real non-root group (`tenant-a`/`ct`/`100`, 2026-09-14). Wired into the Collector to populate `BackupGroup.resolved_name` — closes the manifest §9.4 "aus PVE aufgelöster Name" gap without needing a PVE connection. Still unconfirmed: a *populated* (non-empty) note value end-to-end — none of the 135 real groups checked had one set, only the empty-string case has been observed live.
- **Error responses**: still unconfirmed — every real call made during this verification pass returned `200`, so the non-200 error-body shape has not been exercised against a real server yet.
- **Remote listing** (`GET /api2/json/config/remote`) and **sync job listing** (`GET /api2/json/config/sync`): both reachable (`200`, `{"data": [], "digest": "..."}`) but the tested instance had no remotes or sync jobs configured, so the *content* shape is **unverified — best-effort from PBS documentation only**, unlike everything else in this section. Assumed remote shape: `{"name", "host", "port"?, "comment"?}`. Assumed sync job shape: `{"id", "remote", "remote-store", "store", "schedule"?, "remove-vanished"?, "comment"?}`. `list_remotes()`/`list_sync_jobs()` and the `sync_jobs` table (manifest §8) are built on these assumptions; `tests/test_connectivity_sync_jobs.py` locks in the assumption, not a real capture — its docstring says so explicitly. Also unverified: whether a sync task's `TaskRun.worker_id` (from the already-verified `/tasks` endpoint) can be correlated back to a specific `sync_jobs.job_id` — no real "sync"/"syncjob" task was observed in the live sample (43 backup + 3 prune + 2 prunejob + 1 garbage_collection + 1 verificationjob = 50, no sync), so this correlation is deliberately **not attempted**; the sync-jobs UI shows configured jobs and instance-wide task history side by side, not a precise per-job "last run" figure.

## PVE — verified 2026-09-14 against a real PVE 9.2 cluster

- **Version endpoint** (`GET /api2/json/version`): confirmed. Returns `{"data": {"release": "<string>", "repoid": "<string>", "version": "<string>"}}` — same shape as PBS's version response, exactly as assumed.
- **Auth header** (`Authorization: PVEAPIToken=<value>`, `<value>` = `user@realm!tokenid=secret`): confirmed — note the `=` between token name and secret, unlike PBS's `:`. Both were already correctly distinguished in the existing code; nothing to fix.
- **TLS**: the tested cluster also used a real (Let's Encrypt) certificate, so `tls_trust_mode: "ca"` works — but confirmed live that this means the usual hostname-vs-certificate check applies: connecting by raw IP address failed with `CERTIFICATE_VERIFY_FAILED` (IP address mismatch) even though the same server answered fine over plain TLS, because the cert is issued for a hostname, not the IP. Not a RESURGAM bug — standard TLS behavior — but an operational note: a PVE cluster (or PBS instance) behind a real CA cert must be added by the hostname the cert actually covers, not a bare IP, unless using `tls_trust_mode: "fingerprint"` instead (which skips hostname verification entirely, already supported).
- **Full round-trip confirmed through the app itself**, not just raw `curl`: created a real `PveCluster` via `POST /pve-clusters` and called `POST /pve-clusters/{id}/test-connection` — returned `{"reachable": true, "version": "9.2.11"}` on the first attempt (after fixing the hostname-vs-IP issue above). No code changes were needed — `probe_pve()` and the `/pve-clusters` API surface were correct as originally written.
- **Not yet tested**: anything beyond the version probe — no VM/CT listing, no node/storage listing, no name-resolution capability exists yet for PVE (RESURGAM currently resolves `BackupGroup.resolved_name` from PBS's own group-notes instead, confirmed live already — see the PBS section above). Error-response shape is likewise unconfirmed, same caveat as PBS.
- **PVE 9.2, not 8.x**: the manifest's own target version is "PVE 8.x"; the tested cluster runs 9.2.11. Nothing observed so far suggests an incompatibility, but this hasn't been checked against an actual 8.x cluster.

## File-restore tooling — verified 2026-09-14/15, `proxmox-backup-client` CLI

Originally (2026-09-14) client-tooling verification only, confirming the *capability* manifest §13 (File Indexing/Recovery) would need was real and reachable, ahead of writing any code against it. **Update (2026-09-15)**: that code now exists (`restore-worker/pbs_client/catalog.py`, called in-process from `backend/` — ADR 0011) and has itself been live-verified against the same real PBS instance, which caught three further real bugs the earlier tooling-only pass didn't surface (it never parsed the CLI's actual output, just eyeballed it):

1. `proxmox-backup-client --version` doesn't exist (exits 255, "no such command") — it's the positional subcommand `version`. Affected the Milestone-0 capability check, which had been silently reporting a working install as `degraded`.
2. `catalog dump`'s listing goes to **stderr**, not stdout — stdout is empty on a successful run. A parser reading only stdout (the natural first guess) gets zero entries with no error at all — confirmed the hard way: a live API call against a snapshot already proven non-empty by this same section's own manual testing returned an empty `[]` with HTTP 200.
3. Single-file extraction needs `--ignore-ownership`/`--ignore-permissions` when not running as root (`restore` otherwise fails outright on the first symlink: `failed to set ownership: Operation not permitted`), and `--pattern <path>` restricts `restore` to just the matching file rather than the whole named archive — both real, only discoverable by actually running `restore`/`extract`, which this section's original pass never did (it only ran `catalog dump`, not an actual restore).

None of these were visible from `--help` output or documentation — only from parsing real `stdout`/`stderr` byte-for-byte and running the full extraction path end to end. See ADR 0011 for the full account.

- **Binary**: this sandbox is Zorin OS 18.1 (Ubuntu 24.04 "noble"-based), not Debian, so Proxmox's official APT repo (targets Debian bookworm) was deliberately not registered — a full `apt install` risked shared-library incompatibility. Instead, downloaded `proxmox-backup-client-static_3.4.7-1_amd64.deb` directly from `download.proxmox.com/debian/pbs-client`, verified its SHA256 against the repo's own `Packages` index, and extracted it non-invasively with `dpkg-deb -x` (no system package-database registration, trivially reversible — and in fact already deleted after this test). Confirmed: the statically-linked build runs correctly on this Ubuntu-based sandbox with no missing-library errors. Note: this package bundles `proxmox-backup-client` and `pxar` only — no separate `proxmox-file-restore` binary was present (that's normally a separate `proxmox-backup-restore-image`-style package, not in this repo's amd64 listing as tested); file-level browsing/restore for a CT/host (pxar) backup doesn't need it anyway, see below.
- **Real snapshot listing** (`proxmox-backup-client snapshot list --repository resurgam@pbs!dev@pbs1.example.internal:8007:backup-store --ns tenant-a`): succeeded against the real dev PBS, using the now-elevated `Datastore.Read` token (extended 2026-09-14, was `Datastore.Audit`-only) via `PBS_PASSWORD` env var. Confirms the true underlying datastore name is `backup-store` (the manifest/UI-level "tenant-a" etc. are namespaces within it, not separate datastores).
- **Real file-catalog browsing** (`proxmox-backup-client catalog dump ct/100/2023-09-20T00:00:03Z --ns tenant-a`): succeeded — returned the full guest directory tree (files, sizes, mtimes) of a real, namespaced CT snapshot without needing a full restore first. This is the actual capability manifest §13's File Indexing/Recovery needs for CT/host backups; confirms `Datastore.Read` is sufficient and the data is genuinely browsable per-file, not just per-archive-blob.
- **VM (qemu) disk-image backups**: also now verified — see the dedicated section below. `catalog dump`'s pxar-catalog path (this section) and `proxmox-file-restore`'s block-device-mount path are both confirmed working, against different real backups.
- **No RESURGAM code was written against this yet** — this was tooling/capability verification only, done read-only, all temp files (`.deb`, extracted binaries) deleted afterward.

## VM (qemu) file-restore — verified 2026-09-15, `proxmox-file-restore` CLI against a real PVE 9.2 node

Unlike the CT/host path above, `proxmox-file-restore` couldn't be exercised in this sandbox at all — see ADR 0011 for the full debugging story (an `AF_VSOCK`/AppArmor block in Docker, a zombie-reaping issue, and an intermittent ~10-minute host/guest race that turned out to trace back to mismatched package versions/repos, not a tool bug). Verification instead happened via SSH access to a real PVE 9.2 node (`pveversion`: `pve-manager/9.2.11`), granted specifically for this investigation.

- **Package provenance**: on that real node, `proxmox-backup-client`, `proxmox-backup-file-restore`, `proxmox-backup-restore-image`, and `pve-qemu-kvm` are **all sourced from the same apt repo** (`pve-enterprise`/`pve-no-subscription`), on **Debian 13 (trixie)** — not Debian 12 (bookworm), and not split across the separate PBS-only and PVE-only repos as this sandbox's earlier testing had done. This is the actual root cause of the sandbox's connection race: reproducing a real PVE node's package set requires matching both the repo and the Debian release, not just installing "the latest of each."
- **Real list** (`proxmox-file-restore list 'vm/116/2026-09-14T00:48:57Z' '/drive-sata0.img.fidx/part/2/' --repository resurgam@pbs!dev@pbs1.example.internal:8007:backup-store --ns tenant-a --output-format json`, standalone CLI, RESURGAM's own PBS token, no PVE API involved): succeeded in ~4s (including a cold VM boot), returning a real Windows Server VM's C: drive listing — `Program Files`, `Windows`, `Users`, `pagefile.sys`, `hiberfil.sys`, etc. Browsing worked at every level tested: the disk archive root, its partition table (3 partitions, matching the guest's own boot-log partition scan), and a real NTFS directory.
- **Real extract** (`proxmox-file-restore extract ... - --repository ... --ns tenant-a`, same snapshot): succeeded in under 1s, returning the real content of a small `.ini` file, byte-for-byte matching what was independently confirmed via PVE's own `file-restore/download` REST endpoint.
- **Field shapes corrected**: the Milestone-0 guess for `list`'s JSON output (`{path, type, size}`) was wrong on every field. Real shape: `{filepath, text, leaf, type, size?, mtime?}` — `filepath` is base64-encoded (not a plain path), `text` is the display name, `leaf` is a bool, `type` is a single character (`f`/`d`/`v` observed — `v` is the disk-archive/partition-selector level), and `mtime` is a Unix epoch integer, not an ISO8601 string like the CT/host `catalog` tool uses. `status`'s real shape is `{"Qemu": {"ids": {"<session-name>": {cid, pid, timeout, uptime}}}}`, not the originally-guessed flat list with a `state` field. `restore-worker/pbs_client/file_restore.py` and its tests were updated to match.
- **PVE API tangent**: while comparing against PVE's own `file-restore/list`/`/download` REST endpoints (an alternative architecture ultimately not needed — see ADR 0011), RESURGAM's PVE token got clean `403`s on two missing privileges: `Datastore.AllocateSpace` (on the storage) and `VM.Backup` (on the VM). Both were granted to confirm the full path works; documented in ADR 0011 in case a future design does route through PVE's API.

## PVE restore-execution (EPIC 9, manifest §11.2) — verified 2026-09-17 against the real PVE 9.2 cluster

The first PVE **writes** this codebase makes (everything above is read-only). Verified end-to-end through RESURGAM's own running backend (`POST /restore-plans/{id}/execute` and `/execution/poll`), not just raw `curl` — restoring VM 116/tenant-a's real backup to a brand-new, disposable VMID each time, deleted afterward. See ADR 0014 for the full design.

- **`POST /nodes/{node}/qemu` with `archive=<volid>`** (VM restore-start, real REST equivalent of `qmrestore`): confirmed working exactly as documented — returns `{"data": "<UPID>"}` on success.
- **`GET /nodes/{node}/tasks/{upid}/status`**: confirmed working, including a UPID containing colons passed directly in the URL path — no encoding issue.
- **`PUT /nodes/{node}/qemu/{vmid}/config`** for the post-restore network finalize step: confirmed working.
- **A real, previously-unpredicted privilege gap, found only by running it**: the first live attempt failed `403 Permission check failed (/sdn/zones/LAN/vlan005, SDN.Use)` — restoring a VM whose backed-up network config references an SDN-managed zone requires `SDN.Use` on that zone, checked during the restore itself (before any of RESURGAM's own network-finalize logic runs), not just the privileges already known to be needed (`VM.Allocate`, `Datastore.AllocateSpace`). Granted on the test cluster's `_Custom_RESURGAM` role; same "grant precisely what a live 403 reveals is missing" discipline as ADR 0011's own `Datastore.AllocateSpace`/`VM.Backup` grants.
- **A second gap, found the same way**: applying `name` (see below) requires `VM.Config.Options`, separate from `VM.Config.Disk`/`VM.Config.Network`/`VM.PowerMgmt`.
- **A real, pre-existing bug found by actually running a restore, not by reading the CLI docs**: the restored VM kept its *original* name from the backup archive (`Office-PC`), not RESURGAM's own generated `temp_name` — neither `qmrestore`'s CLI generation (EPIC 8) nor the new EPIC 9 execution call ever passed a name override. Fixed: `POST /nodes/{node}/qemu`'s `name` param (confirmed live) and `POST /nodes/{node}/lxc`'s `hostname` param (CT's name-equivalent — **not yet verified live**, only a VM restore was exercised this pass) are now both set from `temp_name`.
- **Network "none" mode disconnects rather than deletes**, confirmed live: reading the restored VM's real config back via `GET /nodes/{node}/qemu/{vmid}/config` and re-`PUT`ting the same `net0` value with `link_down=1` appended preserves the archive's real NIC identity exactly (confirmed: same MAC, same model, same SDN-managed bridge `vlan005`) while disconnecting it — replacing the original design (`qm set --delete net0`, which removes the device from the guest entirely) and CT's own previous hardcoded-`vmbr0` fallback for the same case.

## Still open

- **PBS error responses**: every real PBS call in this verification pass returned `200`, so the non-200 error-body shape is unconfirmed.
- **PBS `list_remotes()`/`list_sync_jobs()`**: reachable but empty on the tested instance — field shapes remain best-effort from documentation only (see the PBS section above).
- **PVE beyond the version probe**: no code exists yet for VM/CT listing, node/storage listing, or anything else PVE-side — nothing to verify until that code is written.
- **VM (qemu) file-restore**: now confirmed working (see the dedicated section above), but only via direct SSH testing on a real PVE node — not yet exercised through RESURGAM's own running backend end-to-end (that would need this sandbox to have matched package versions installed, which it deliberately doesn't; `restore-worker`'s tests mock the CLI boundary using real captured fixtures instead, same pattern as the CT/host path). CT/host (pxar-based) file browsing *and download* are confirmed working end-to-end through RESURGAM's own code (`catalog.py`, ADR 0011), not just the raw CLI.
- **CT/LXC restore-execution** (EPIC 9): only the VM path was exercised in the 2026-09-17 live pass above. `POST /nodes/{node}/lxc`'s `restore=1`/`hostname`/inline-`net0` params are still the documented-but-unverified default (`restore/execution.py`'s `CT_RESTORE_SUPPORTS_INLINE_NET0` flag) — needs its own live restore of a real CT before being trusted the same way the VM path now is.
