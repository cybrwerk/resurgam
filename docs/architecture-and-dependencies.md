File Indexing was then actually deployed and driven against real VM content for the first time, surfacing four more real bugs baked into the original VM-path design, none caught by the CT/host-only live verification above: (1) `proxmox-file-restore list` returns a `{"code":..., "message":...}` JSON *object*, not an array, for a partition it can't mount (confirmed live: a real Windows VM's EFI/recovery partition) — the old code blindly iterated it as entries, producing an opaque `TypeError`; fixed with a new `PathNotMountableError` in `restore-worker`'s `pbs_client`, skipped per-path by the walker rather than failing the whole job (the same code path also transparently covers an encrypted disk RESURGAM has no key for, though that's not yet live-verified against a real encrypted VM). (2) A single real directory can hold thousands of files (confirmed live: one flat package-doc directory alone had 5,900+), and the VM path's insert wasn't chunked like CT/host's already was — one un-chunked multi-row INSERT blew past Postgres's 65,535-bound-parameters-per-statement limit and crashed the job; fixed by chunking it identically. (3) The resulting driver error's `str(exc)` embedded the entire failed statement and every parameter, producing a 2.95MB `error_message` that broke a plain `SELECT *` against the row — fixed with a general `_format_error_message` truncation helper used at both of the worker's exception sites, not just this one. (4) `/usr/bin/X11`, a classic self-referential symlink, was walked as if it were an ordinary directory (PBS reports it `leaf=False`, same as a real one) — `browsable_paths()` filtered only on `leaf`, not `type`, so the walker descended `/X11/X11/X11/...` until the per-run directory budget cut it off, burning an entire run's budget on one loop; fixed by excluding symlinks from traversal by `type`, regardless of `leaf` (still indexed as their own entry, just never followed). Once VM indexing was actually running cleanly, two further improvements followed directly from watching it against a real, large Ubuntu VM: per-VM regex exclusion patterns (`BackupGroup.file_index_exclude_patterns`, migration 0024, a new `POST .../file-index-exclude-patterns` endpoint validating each pattern compiles before saving) let an irrelevant subtree (a real `/usr/src` kernel-headers tree) be pruned from both the walk itself (VM — saves the actual subprocess cost, not just index size) and the bulk catalog dump (CT/host, index-size-only); and "reuse and link" (`FileIndexEntry.linked_from_entry_id`, migration 0025) — when a newly discovered entry's `(type, size_bytes, mtime)` exactly matches the most recently indexed entry at the same path for that group, the new row links to it (always to a *root*, never chained) instead of duplicating its `size_bytes`/`mtime`, resolved back out via a small batched join at browse/search time. This has a genuine correctness interaction with both places that can delete `file_index_entries` (the age-based retention sweep and the collector's orphaned-snapshot purge): a `not_still_linked()` helper, shared by both, skips any row a newer row still depends on, backstopped by `ON DELETE RESTRICT` on the self-referencing FK (deliberately not `CASCADE`, unlike every other FK on this table) — confirmed via AskUserQuestion with the user as the accepted tradeoff, meaning `retention_days` becomes a floor rather than an exact cutoff for a row still referenced, and an orphaned snapshot's browse/search can in principle still surface one stale linked-to row until whatever depends on it is itself retired. ## Non-negotiable architectural commitments (carried across all milestones)

These constraints apply to every future milestone regardless of which component is being built, and must not be silently dropped during implementation:

- **Self-signed certificate support.** PBS and PVE connections must support TLS trust via a pinned fingerprint, not only standard CA validation (manifest §6.1/§6.2). Implemented: `net/tls_pinning.py` does a real raw-socket TLS preflight and SHA-256 fingerprint compare before any request is sent, tested against an actual locally-generated self-signed certificate.
- **OIDC + RBAC + multi-tenancy are mandatory.** Every Control Plane endpoint enforces role and customer scope server-side (manifest §7). Implemented: real OIDC via authentik (ADR 0007) alongside the permanent break-glass path (ADR 0004), both feeding the same session/RBAC interface.
- **Packaging split: Docker for app/API/DB, baremetal/nested-VM for the Restore Worker.** The API, UI, database, and queue-adjacent services are pluggable Docker/Podman Compose containers; the Restore Worker runs natively as a systemd service (manifest §5.3) because it needs direct `/dev/kvm`/`/dev/fuse` access that containerization would complicate, and because privileged PBS-CLI execution is deliberately kept outside the containerized, non-root Control Plane (manifest §3, §4.1).

## Security-relevant boundaries already in effect

- The Restore Worker never invokes a shell (`shell=True` is forbidden); all subprocess calls use explicit argument lists.
- The Control Plane executes no PBS/PVE CLI tools itself, and does not yet talk to the Restore Worker at all — that link doesn't exist yet. It does make direct outbound REST calls to PBS/PVE for connection testing (see above), which is within manifest scope (§6.1).
- No backup content is stored by RESURGAM itself; PBS/PVE remain systems of record.
- Every Control Plane endpoint returns a typed Pydantic response model, never a raw dict, and every error (domain, HTTP, or unexpected) is normalized into `{code, message, correlation_id, details}` with an `X-Request-ID` correlation ID on every response (manifest §4.2).
- `audit_events` rows are immutable at the database level (a Postgres trigger rejects `UPDATE`/`DELETE`, not just an omission in application code) — manifest §8.
- No API token or password is stored in plaintext in PostgreSQL; `secret_references` holds only an opaque pointer, PBS/PVE tokens are Fernet-encrypted at rest via the interim local secrets provider (ADR 0005, not a substitute for a real secrets provider), and the break-glass password is a bcrypt hash from configuration.
- `pbs_instances`/`pve_clusters` create rejects the request (nothing is persisted) if the operator-confirmed TLS fingerprint doesn't match what's actually observed on re-probe at creation time — closes the gap between "probe" and "confirm". `PATCH` on both (2026-09-14, added for the frontend's new edit-in-a-modal flow) re-verifies the same way, but only when a connection-relevant field (`host`/`port`/`tls_fingerprint_sha256`) is actually part of the request — editing just a display name doesn't re-probe a host that isn't changing. Every field is optional on `PATCH` (a real partial update, an omitted field leaves the stored value alone); `api_token`, if given, rotates the secret in place — no endpoint ever returns a stored token, so the frontend's edit form always starts that field blank with a "leave blank to keep the current value" hint, never a stale or masked value.
- PBS/PVE connection endpoints (`pbs_instances`, `pve_clusters`) stay `platform_admin`-only for both reads and writes.
- `GET /api/v1/datastores` and `GET /api/v1/datastores/{id}` are server-side filtered by the caller's customer-scoped role assignments (manifest §7: scope must be enforced server-side, never only in a client) — a `platform_admin` sees everything, anyone else only datastores assigned to a customer they hold a role at. An out-of-scope datastore 404s rather than 403s, so a caller can't distinguish "doesn't exist" from "exists but isn't yours."
- Importing a datastore re-fetches its details live from the PBS instance rather than trusting client-supplied `path`/`comment` — the same "server re-verifies, never trusts the client" pattern as the TLS fingerprint confirm flow.
- The Collector (`collector/sync.py`) is idempotent by construction — every write is an upsert keyed by PBS's own identifiers (backup-type/id/namespace, snapshot time, task UPID), never a blind insert — but does not detect or remove rows for snapshots pruned from PBS since the last sync (a stated simplification, not a silent gap).
- `connectivity.pbs_api.list_snapshots()` queries every namespace explicitly (`list_namespaces()` first, then `?ns=<name>` per namespace) rather than a single unscoped call — confirmed live (2026-09-14) that `/admin/datastore/{store}/snapshots` is scoped to exactly one namespace per call and does not recurse (a `max-depth` parameter was tried and rejected by PBS outright). Before this fix, a datastore with an empty root namespace but real backups entirely under other namespaces looked completely empty to RESURGAM — confirmed on the same real PBS instance, which had 135 backup groups and 1317 snapshots invisible under `tenant-a`/`site-b/tenant-b`/`site-b/Firestorm` until fixed. Falls back to root-only if namespace listing itself is unreachable, rather than failing outright.
- The PBS connectivity layer (`connectivity/pbs_api.py`) is now verified against a real PBS 4.2 instance (2026-09-13/14), not just fixtures — see [`milestone-1-pbs-pve-api-assumptions.md`](./milestone-1-pbs-pve-api-assumptions.md). This caught a real bug (`list_tasks` used the wrong JSON field names and would `KeyError` on every real call), a task-classification gap (scheduled jobs report a distinct, `"...job"`-suffixed `worker_type`), and the namespace-scoping bug documented above. `list_tasks` now requests up to 2000 tasks per sync (PBS defaults to 50) but does not paginate further — an instance with more history than that since its last sync will still miss the oldest entries, a stated simplification. **PVE connectivity is also now verified** (2026-09-14, against a real PVE 9.2 cluster) — `probe_pve()` and the full `/pve-clusters` create + test-connection flow worked correctly on the first real attempt; only the version probe exists so far, no VM/CT listing or name resolution via PVE yet (RESURGAM resolves `BackupGroup.resolved_name` from PBS's own group-notes instead, see above). One operational finding, not a RESURGAM bug: connecting to a real-CA-certificate PVE/PBS host by its bare IP address fails standard TLS hostname verification — it must be added by the hostname the certificate actually covers, or via `tls_trust_mode: "fingerprint"` instead.

PVE-sourced backups (vzdump) commonly write the VM/CT name into this same field, so this closes the gap without a PVE connection.

A failed login redirects to `{FRONTEND_ORIGIN}/login?oidc_error=<code>` with no token material at all.
- `CORSMiddleware` allows exactly one origin, `FRONTEND_ORIGIN` (no wildcard), and is the outermost middleware in `main.py`'s stack.

- `usage_measurements` (manifest §9.3/§8) is genuinely append-only — no code path ever updates an existing row, only inserts a new one per Collector sync (on-demand, ADR 0006). `used_bytes`/`available_bytes`/`total_bytes` come from a real PBS call (`list_datastore_usage`, confirmed live) and are physical, deduplicated-and-compressed disk usage (manifest's "PBS-Datastore-Belegung"); `logical_bytes`, the manifest's separately-named "logisch geschützte Datenmenge", is the undeduplicated sum of current snapshot sizes computed from RESURGAM's own `backup_snapshots` table — the gap between the two figures is the dedup/compression ratio, surfaced in the frontend's Capacity & Trends page. The manifest's other two distinctions (underlying filesystem usage; temporary restore storage) aren't separately tracked — the former is assumed identical to PBS's own numbers since a datastore is its own filesystem mountpoint, the latter has no restore-worker integration yet to measure. Group/snapshot counts and `last_successful_gc_at` are likewise computed from RESURGAM's own already-synced tables, not a second PBS round-trip. `GET /datastores/{id}/usage` reuses the same customer-scope check as `/datastores`. Daily/monthly change (`inventory/usage.py`) is computed from RESURGAM's own stored history, not PBS's own richer built-in `history` array (real, confirmed live, but deliberately not parsed here — see `pbs_api.list_datastore_usage`'s docstring) — a stated simplification that returns `null` rather than a misleading `0` once enough history hasn't accumulated yet. This live verification also caught a real, separate bug: `BackupSnapshot.size_bytes` was `Integer` (INT4, ~2.1GB max) when real snapshot/datastore byte counts routinely exceed that — widened to `BigInteger` in the same migration (0008) as the new table.
- Billing foundations (not from the manifest — ADR 0009): `DatastoreCustomerAssignment.role` (`primary`/`offsite`) lets a customer's per-VM billing count exclude a secondary/DR copy of the same datastore without needing cross-PBS-instance VM identity matching (rejected as a tenant-isolation risk — VMIDs aren't unique across instances). `BackupGroup.customer_id` is a nullable per-group override of the datastore's own customer assignment — resolved by `auth/scope.py::effective_group_customer_id()` (group override, else datastore assignment, else none). `GET /datastores/{id}/backup-groups` filters per-group by this effective customer rather than gating on "is the whole datastore in scope" — a shared datastore can expose only the caller's own groups even when the datastore itself belongs to a different customer, and 404s the whole listing only when *nothing* in it is visible to the caller (preserving "don't confirm existence of an out-of-scope object" at the finer granularity). `GET /backup-groups/{id}/snapshots` and `/backup-groups/{id}/assign-policy`'s customer-match check were updated the same way. `pricing_plans` (global default when `customer_id` is null, else a per-customer override) enforces "at most one global plan" and "at most one plan per customer" with partial unique indexes, since a plain `UNIQUE` constraint treats every `NULL` as distinct in Postgres and wouldn't actually prevent multiple global plans. The computation itself followed on 2026-09-14 (`inventory/billing.py::compute_customer_billing()`, `GET /billing/customers[/{id}]`, customer-scope filtered the same way as `/alarms`): per customer, the per-VM fee counts `primary`-role groups only (own override, else the datastore's assignment; a datastore with no assignment row defaults to `primary`, the same default the column itself uses); the per-GB fee counts every matching group regardless of role, scaling each group's own logical bytes (its snapshots' summed `size_bytes`) by *its own datastore's* dedup ratio rather than one ratio applied datastore-agnostically, since a customer's VMs can span datastores with different dedup characteristics. A datastore with no usage measurement yet contributes 0 bytes for its groups and sets `physical_bytes_estimate_complete: false` instead of blocking the response — same "partial, not blocked" philosophy as `compute_usage_changes` returning `None`. `estimated_monthly_cost` is quantized to 2 decimal places (a live smoke test against real data first surfaced an unrounded `Decimal` result with 13 digits after the point). Verified against real data on the dev PBS: 135 backup groups, ~2.16TB estimated physical bytes, cost matching `135 × price_per_vm + 2159.46GB × price_per_gb` exactly. No invoice/report generation yet — this is the computation, not billing output.

- Alarms (`GET /alarms`, manifest §9.2's "überfällige Backups"/"Datastore-Auslastung") are computed fresh on every request (`inventory/alarms.py::compute_alarms()`), never stored — same "computed on read" pattern as `protection_status`/usage changes. Two signals only: a backup group's `protection_status` being `critical`/`warning` (skipped entirely if no policy is assigned — matches the existing "no policy means UNKNOWN, not an alarm" rule), and a datastore's latest `UsageMeasurement` crossing 80%/95% used (thresholds kept in sync by hand with the frontend's `usagePercentTone`, no shared constant yet). - Local user accounts + MFA (not from the manifest — ADR 0010, requested directly: "For Local-Users there must be MFA with FIDO, TOTP and/or Recovery-Codes... there is no profile site to change password"). `User.password_hash` (nullable, set only for a real local account) is a fourth way a `User` row authenticates alongside break-glass (`is_breakglass`) and OIDC (`external_subject`) — break-glass itself is untouched, still the single env-configured emergency credential, still exempt from MFA (there's no per-user row for it to attach a TOTP secret to), still unable to change its own password (`/auth/change-password` explicitly rejects it with `no_local_password`). `POST /users` (`platform_admin`-only) creates a local account with an admin-set initial password; a fresh account has zero role assignments until `POST /users/{id}/assign-role` grants one — it can authenticate but reach nothing. `POST /auth/local-login` returns a real session directly when no MFA method is confirmed (identical shape to today), or a short-lived (5 min) **MFA challenge token** otherwise — a JWT carrying `purpose: "mfa_challenge"`, which `verify_session_token()` explicitly refuses to accept as a real session, so it can only reach the three `/auth/mfa/verify-*` endpoints, nothing else. WebAuthn registration/authentication ceremonies need the server to remember its own random challenge between the "generate options" and "verify response" calls; rather than add RESURGAM's first piece of server-side session state, the challenge (and, for registration, the chosen nickname) rides back to the client inside another purpose-scoped JWT (`create_webauthn_ceremony_token`, `action: "register"`/`"authenticate"` so one can't be replayed as the other) — an early version concatenated the nickname onto the raw challenge bytes with a `|` delimiter, which intermittently corrupted the split because the challenge is random bytes that can legitimately contain that exact byte (caught by a real, initially-flaky test failure, fixed by giving the nickname its own JWT claim). TOTP secrets are stored via the same `SecretReference`/`LocalEncryptedSecretsProvider` mechanism as PBS/PVE API tokens (ADR 0005), not a new one; `TotpCredential.confirmed_at` stays null until the user proves the secret works once, so a mis-scanned QR code never silently becomes a login requirement. Recovery-code generation (`POST /mfa/recovery-codes/generate`) is rejected unless a confirmed TOTP credential or a registered WebAuthn credential already exists — codes back up an existing second factor, they aren't one on their own. Tests mock `webauthn.verify_registration_response`/`verify_authentication_response` at the call site rather than hand-rolling a fake authenticator's CBOR/COSE attestation encoding — that would test the third-party library, not RESURGAM's own ceremony-token/storage/error-path wiring; every other new surface (local login, change-password, TOTP, recovery codes) is tested with real bcrypt hashing, real `pyotp` TOTP generation, and a real Fernet secret round-trip, no mocking.
